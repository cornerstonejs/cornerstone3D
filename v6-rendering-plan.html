Cornerstone 6 rendering plan: slice first

An audit of the rendering switches and device checks on main (5.18.3), and a plan for a breaking v6 on the next viewports. Written 2026-11-14. Every number is from one Mac (Apple M2 Ultra, Chrome 157) unless its row says otherwise. I measured no phone and no tablet.

  • Step 1, slice first for the source image: built, and on by default since 2026-11-16 (your decision). rendering.planar.sliceFirst: false turns it off.
  • Step 2, the draw step made safe: built. Texture probes that compare values, the 16-bit scale fix, context restore, one sampler for both draw steps, a self-test page.
  • Step 3, the router: built, per layer. viewport.getRenderPlan() gives the path and the reason of each layer. A layer leaves the 3D texture only when the device cannot draw it exactly there, and then gets an exact slab from the CPU in small steps.

1. Why devices fail today

Issue #3020 names four kinds of GPU failure. Each one has the same cause on our side.

FailureWhat the user seesWhy it happens on mainWith slice first
1. A texture edge is too large A grey or black viewport. No event. The 3D texture has the size of the volume. MAX_3D_TEXTURE_SIZE is never read, and some devices report a limit they cannot draw. A 2D view holds a 2D image. Its edge is a slice edge. An image above the 2D limit is split into tiles, which loses nothing.
2. The context runs out of memory The WebGL context is lost. Each volume on screen is on the GPU in full: 2 bytes per voxel with norm16, 4 bytes without it. About 0.1 to 1.5 MiB for each layer of each viewport.
3. The browser runs out of GPU memory The tab or the GPU process dies. No event. The same textures, plus 7 WebGL contexts made at start. One context. The big texture exists only for a slab or 3D, after a check.
4. A texture format lies A wrong image. No event. 16-bit data needs EXT_texture_norm16 or float filtering. The probe checks "not black" and the 2D path does not use the probe. Only formats that every WebGL2 device must have. One draw program, tested with exact values at start.

Issues in this family: #2029 (Samsung A series), #1759 and #2212 (Android grey and black images), #1133 (iPhone SE), #2653 (iOS 18 volume rendering), #2530, #2153 and #453 (lost contexts), #1360 and #119 (texture size), #978 (big images on small devices), #805 and #839 (memory), #1397 (wrong Hounsfield values with norm16), #3020 and #3034 (automatic limits and budgets).

2. Audit: what main does today

2.1 The four render paths of the planar viewport

Each path does two jobs in one piece of code: it finds the pixels of the slice, and it draws them. That is why the paths do not have the same features.

2.2 How a path is chosen

  • Two inputs only. Does the data have a volume, or is the view off the acquisition plane? And is the backend gpu or cpu? That is all PlanarRenderPathDecisionService reads.
  • What it does not read: the size of the data, the limits of the device, the slab thickness, or whether the GPU path worked last time.
  • auto means GPU unless no WebGL2 context can be made.
  • No automatic change. The code says "Cornerstone never switches render backends on its own". The app must listen for a lost context and call setRenderBackend('cpu').

2.3 What the library knows about the device

  • getRenderingCapabilities() probes six texture formats one time and stores the result per GPU name. The code uses only webgl, norm16 together with norm16Linear, and floatLinear.
  • The probe is weak. It draws a 5 x 1 texture and passes when the pixel is grey and not black. It does not compare values, and it tests no 3D texture and no size.
  • The 2D path skips it. VtkImageMapperRenderPath lets vtk.js turn norm16 on from the extension alone. The comment says the gate is "intentionally not wired in here".
  • No GPU tier. detect-gpu is gone from the code. Only the 2.x migration guide still shows gpuTier.
  • GPU presets do not look at the device. setGpuSettingsPreset has low-tablet, low, medium and high. The app must pick one, and they apply only when lossyDownsampling.final is on.

2.4 Rendering engines and canvases

  • Two engine modes. contextPool (default) and tiled.
  • Seven contexts at start. The pool makes all of them in its constructor. Next planar and 3D viewports all draw on context 0, because a volume texture cannot be shared between contexts. So on next the other six give nothing.
  • isMobile is manual. It only sets the pool to one context, and nothing detects it. A comment in the touchAllTools example says iOS evicts pages that hold several live contexts.
  • No size guard. Nothing clamps devicePixelRatio or the canvas size. maxTextureSize is probed and never read.
  • One canvas shows at a time. A next planar viewport has a GPU canvas and a hidden CPU canvas. It cannot draw a GPU layer and a CPU layer together.

2.5 4D today

  • CPU memory: every time point is requested and stays decoded. The only bound is the cache, 3 GB by default.
  • GPU: one 3D texture the size of one time point. A change of time point uploads the whole texture again, slice by slice, on the main thread.
  • Next GPU path: by my reading of the code it uploads the whole time point on every rebuild of the mapper, so on a scroll or a window change too. The dynamic branch of update3DFromRaw has no dirty check. I did not run this.
  • Next CPU path: it does not redraw when the time point changes.
  • Cine: playClip plays time only for the legacy VolumeViewport. On a next viewport it scrolls slices. Nothing preloads for playback.

2.7 Defects I found that are worth fixing on main whatever we decide

All from reading the code. I ran none of them on a device that fails.

  1. The 2D image path of next does not use the capability probe. A device with a broken norm16 extension can still get it. GenericViewport/Planar/VtkImageMapperRenderPath.ts, the comment above the mapper.
  2. The probe passes on "grey and not black". utilities/textureSupport.ts, return r === g && g === b && r !== 0.
  3. No limit is checked and no error is read. MAX_3D_TEXTURE_SIZE has no reader. There is no gl.getError() in packages/*/src. A texture that fails gives a grey or black view with no event.
  4. Nothing recovers from a lost context. The events are forwarded and no code listens. vtk.js rebuilds no texture when the context comes back.
  5. Seven contexts are made at start, and next viewports use one.
  6. A 16-bit volume without usable norm16 goes up as 32-bit float. That is twice the GPU memory, and each slice is copied to a Float32Array first.
  7. A GPU capability changes what the loader stores. canRenderFloatTextures() picks Float32 or integer voxels and can turn prescaling off (dicomImageLoader/src/imageLoader/createImage.ts, utilities/generateVolumePropsFromImageIds.ts). The loader should not depend on the GPU.
  8. The CPU volume path keeps a full copy of the volume for an axis-aligned view (PlanarCPUScalarViewportSampler.ts). On a weak device that is the wrong place to double the memory.
  9. 4D uploads far too much. See 2.5.
  10. volumeModifiedThrottleMs is 5000 in init.ts and the type comment says 50.
  11. Dead names: the render modes webgl2d and vtkVolume, PlanarRenderPathDecisionOptions.useSliceRendering, the loader option progressiveRendering, and the capability fields maxTextureSize, float, halfFloat, halfFloatLinear.
  12. Stale docs: concepts/cornerstone-core/renderingEngine.md shows config names that no longer exist.

3. The v6 design

3.1 Five rules

  1. A 2D view needs a 2D image. The GPU holds what the view shows. It holds a volume only when the view asks for a thick slab or 3D.
  2. The pixels are exact by default on every device. A reduced image is opt-in and always labelled. This is the rule of today and it does not change.
  3. Cornerstone changes the path by itself only when the new path draws the same pixels. This replaces "never switches on its own". A change that loses nothing needs no question to the user. The rules that keep such a change stable are in 3.3.
  4. Believe what was measured, not what the device says. Check where the resource is made, and remember what failed.
  5. The app says what it wants to see, not how to render it. Orientation, slab, blend mode and time point are the inputs. There are no device flags.

3.2 Two steps: sample, then draw

Today each render path does both steps, so there are four paths with four feature sets. In v6 the steps are separate and any way to sample works with any way to draw.

  • A straight cut is a copy. A sagittal or coronal plane lies on a row or a column of voxels, so no value has to be computed. The sampler of today has no short path for that. It runs its general loop and takes 1 to 2.5 ms. A plain copy gives the same values in 0.5 ms for sagittal and in under 0.1 ms for coronal, on a 311 slice CT. v6 adds that short path inside sampleVolumeGrid. The numbers are in section 9.
  • What this fixes at once: the CPU path gets slabs, fusion and slice labelmaps, because those live in step 1 and in a small shared draw contract. Today each of the four paths has to build them again.
  • Layers: the source, a fusion overlay and a labelmap are each one 2D image with its own place in the view plane. Each keeps its own resolution. They are drawn in order, so there is no depth test and no depth offset. The bug of #3077 cannot happen.
  • World coordinates: unchanged. They come from the camera. Probe and ROI values come from the CPU data, as they do on the stack path today.

When to draw on the CPU

  • No WebGL2 context.
  • The self-test of the draw program fails.
  • The context is lost and does not come back.
  • A test pins it on one viewport.

When to mix CPU sampling and GPU drawing

  • Always, for every slice that is not an acquired frame.
  • It is the default path on every device, not a fallback.
  • A thin slab uses it too. The router estimates the CPU time from the slab depth and the image size and stays on the CPU under about 50 ms.

When to sample on the GPU: only for a thick slab and for 3D, and only after the check in 3.4. I would not add "use the GPU volume to speed up plain slices" in 6.0. Both ways are exact, so the router can add it later if the device numbers ask for it.

How a change of path stays stable. Rule 3 is only acceptable if the change is proper and stable. These are the rules for it:

  • Same pixels only. The router changes a path by itself only when the new path draws the same pixels. The picture does not change. Only the speed can.
  • Down, and it stays down. A failure moves the viewport one step down. It does not go back up by itself in that session, so a path cannot flip back and forth. A new page load, or a call from the app, tries the upper path again.
  • No empty frame. The image on screen stays until the new path has drawn.
  • Only at known moments. When data is added, when the view asks for something else (a slab, 3D), and when something fails. Never on each frame.
  • For each viewport. There is no global CPU or GPU mode. Two viewports of one layout can be on different paths: a plain slice next to a MIP. One viewport that moves down leaves the others alone, unless they share the cause, as with a lost context.
  • One event for each change, with the reason. getRenderPlan() gives the same answer at any time.
  • The change is tested. The test suite forces each failure and compares the picture before and after: a lost context through the WEBGL_lose_context extension, a self-test that fails, and a texture that is refused.

3.4 How the router knows the device

  • For drawing: one self-test. At start, draw a known 16-bit pattern through the real draw path, read it back, and compare the exact values. A failure means CPU drawing. Here it took about 0.1 s the first time, almost all of it the shader compile that the page needs anyway. The result is stored per GPU name and browser version.
  • For the GPU volume texture: check where it is made.
    • Before: each edge against the largest edge that this device has drawn correctly. A thin probe texture extends that record when a bigger edge is needed, as #3020 proposes.
    • After: read the GL error, and read back one known value.
    • A marker in browser storage is written before a big allocation and cleared after it. If the page starts and finds the marker, the last attempt killed the tab. That size is recorded as failed. This catches failure 3, which sends no event.
  • What is stored: the largest size that worked and the smallest that failed, per GPU name and browser version. No presets and no app input.
  • A wrong guess costs speed, not correctness. The step below on the ladder is exact. This is why learning by failure is safe here and was not safe when the only fallback was a reduced image.
  • A lost context: the draw step makes its program again and uploads the visible 2D images again from the CPU cache. That is a few milliseconds and needs no app code. A GPU volume texture is tried one more time, then the view moves down the ladder.

3.5 The draw step: the vtk.js image mapper, behind a seam

Decided in the review: the vtk.js image mapper stays as the draw step. It is not replaced. The design keeps a narrow seam, so that it can be replaced later if you want that.

  • The seam: the sample step hands over a plain object, a typed array of raw values with its place in the world. It holds no vtk.js type. One file draws it with the image mapper. A new draw step replaces that one file and nothing else.
  • The same seam serves the CPU draw step. Canvas2D takes the same sampled slice.

What the image mapper leaves open, and what we do about it:

  • It picks the 16-bit format by itself, from what the device lists. Norm16, if the device lists that extension. If not, 32-bit float, which a device can smooth only when it lists a second extension. If that one is missing too, half float, but only when the values fit, because half float holds whole numbers only up to 2,048.
  • Its one check does not compare values. For norm16 it draws a texture of two pixels and passes when the pixel it reads is not black. A device that returns a wrong value passes. Our own probe is not used on this path.
  • The safe format cannot go through it. An integer texture needs no extension and is exact on every WebGL2 device. It needs a shader that reads whole numbers and blends them itself. The shader of the image mapper lets the hardware blend, so it cannot read one.
  • Each layer is an actor in a 3D scene. The image, the fusion overlay and the labelmap are sorted by depth. #3077 is a bug of that kind. A 2D program draws the layers in order.
  • What we do now: use our own probe on this path, and make the probe compare values. That closes the norm16 case. The other two formats stay as vtk.js picks them.

If the draw step is replaced one day, this is what an own WebGL2 program would give. It is not planned.

  • Formats that every WebGL2 device must have: 16-bit data goes into an integer texture (R16I, R16UI). The shader reads the four neighbours with texelFetch and blends them itself. No extension is involved.
  • Measured here: 0 of 65,536 values wrong, and the blended image equals a CPU reference in every pixel. Half float, the only core 16-bit format that the hardware can filter, got 53,247 of 65,536 values wrong and 512 values inside the CT range. The cost to draw was too small to measure on this GPU.
  • We can only test what we control. One program means one self-test covers every 2D view. vtk.js builds its shaders from many parts.
  • No copies: the texture is filled from the cached frame and reused. Today the image mapper makes the texture again on each change and the actor keeps a second copy of the pixels.
  • One WebGL2 context draws every 2D view of a rendering engine. The vtk.js context is made only when a view needs a thick slab or 3D, or when a legacy viewport is enabled. The pool of seven is no longer made at start.
  • Device limits handled inside: an image above MAX_TEXTURE_SIZE is drawn as tiles. The canvas size is clamped to what the device allows.
  • WebGPU later is one more small program on the same inputs. It does not wait for vtk.js or vtk-wasm.

3.6 The GPU volume path becomes a module

  • What it keeps: the streaming 3D texture, the reslice mapper for slabs and the volume mapper for 3D, all on vtk.js as today.
  • When it loads: only when a view needs a thick slab or 3D.
  • What stays from the multi-resolution work (#2931): the reduced textures, the fidelity record and the indicator. They now apply to slabs and 3D only. The acquired-frames path is no longer needed, because every plane is exact, not only the acquisition plane.
  • It fits #2894. That issue asks for rendering as a separate package so that vtk-wasm can replace vtk.js. With slice first the part that must be replaced is much smaller.

  • A pin on one viewport stays, so that the test suite can run every path. An app does not need it.

3.8 Slices ready before the scroll

The idea from the review: prepare the previous and the next slices, so that a scroll never waits. I agree. I would build it as a cache first and put the worker behind it second.

  • What it is: a small cache of sampled slices for each viewport. It holds the slice on screen, a few slices before and after it, and for 4D the same slice of the next time points. Step 1 looks there first.
  • What it costs: a sagittal slice of a 311 slice CT is 0.3 MiB. Five slices on each side are about 3 MiB for a viewport.
  • Where it helps: tilted planes, thin slabs, 4D playback and slow devices. A straight sagittal or coronal cut is already under 1 ms here, so on a desktop there is nothing to wait for.
  • Where the work runs first: on the main thread, in idle time, in the direction of the scroll.
  • Why not a worker from the start: a worker cannot read the frames today. They live on the main thread and core uses no shared memory. A copy of the volume for the worker doubles the memory, which is what a phone has least of. Shared memory needs a page that is cross-origin isolated, and many deployments cannot set that.
  • When a worker does it: on a page that is cross-origin isolated, where the frames can sit in shared memory. And for slabs on any page, where one cut takes tens of milliseconds and only the frames of the slab have to be sent.
  • It is the same cache that a server needs. A sampler that answers late, such as a worker, bricks or a server, is usable only if the neighbours are asked for early. So step 1 is asynchronous from the start, and this cache is part of the design and not an extra.
  • What clears a slice: an edit of the voxels, such as a labelmap brush. A frame that arrives late. A new plane.

4. 4D

In v6 time is one more input of step 1. Nothing else changes.

  • A change of time point costs three small samples, not one volume upload. The axial view takes the frame itself. The sagittal and coronal views copy one row or column out of each frame of that time point. That is an exact copy of a few hundred kilobytes.
  • Any plane works, oblique too, because it is the same sampler.
  • Smooth playback: keep the sampled slices of each time point for the planes on screen. For 30 time points and three planes that is about 12 to 45 MiB. Playing is then only a texture swap. The cache fills ahead of the playhead.
  • Memory with a bound: keep decoded frames only for the time points near the playhead. Once the slice cache is full, playback at a fixed position needs no decoded volume at all. A move to a new slice position needs the current time point first, and the others refill.
  • An example: a 4D CT with 10 phases of 300 slices is 1.5 GB decoded today. With a window of three phases it is about 450 MB plus the slice cache.
  • Work that is needed either way: a dynamic context of playClip for next viewports, a redraw on a time point change, and frames that wait for their time point to load.
  • One more, found in this review: the sampler reads a 4D volume one voxel at a time today, because the voxel manager of a 4D volume does not hand out whole frames. It needs the same direct read that a plain volume has. I did not time it.
  • The slices of the next time points come from the cache of 3.8.

5. Server side, later

I would not design it now. v6 only has to leave the right opening, and step 1 is that opening.

  • The question a server answers is the same one the CPU sampler answers: "give me the 2D image for this plane, this time point and this slab".
  • The client still draws. The server sends raw values, lossless, not a picture of the screen. Window, zoom and pan stay local and instant. A request is needed only when the slice changes.
  • 3D from a server is a colour image into the same draw step.
  • Bricks use the same opening on the client. A volume made of bricks answers the sampler with only the bricks that the plane cuts. That is the reslicer that the brick loader design asks for.
  • What v6 must do now to keep this open:
    • Step 1 can be asynchronous and can be cancelled.
    • Step 2 accepts an image that arrives late, or a coarse one first.
    • Tools never read pixels from the GPU. Values come from the data source.
    • The view state stays on the client.
  • Not in this plan: connections, protocols, sessions and cost.

6.1 The migration guide

You asked that every breaking change of v6 is documented. The guide is in the docs, next to the guides of the earlier versions: packages/docs/docs/migration-guides/6x/. It holds the changes that are in the code today, and a section for what is decided and not in the code yet. A stage is not done until its changes are in the guide. The changes in it today:

  • Slice first is on by default for next planar viewports, and what getRenderPlan() tells.
  • The CPU picture is the GPU picture: same colours and opacity, the background colour of the viewport around the image (it was black), and no VOI lookup table of the image (the GPU never applied it).
  • The labelmap fill is drawn as configured. A legacy volume viewport drew it at about half the configured alpha (0.5 looked like 0.26). Accepted on 2026-11-16.
  • Image defaults: a MONOCHROME1 image starts inverted, an image without a window gets its pixel range (it was 0 to 255).
  • Whole slide: world points follow the coordinate system of the slide, and canvas points are right at any device pixel ratio.
  • 3D: a reset fits like the first mount, and setViewReference moves the camera.
  • Video: view references carry the camera, STACK_NEW_IMAGE fires for each frame, options.frameNumber is honoured.
  • Float data on iOS: PT stays in floats and is drawn with nearest filtering where the device cannot filter float textures.
  • Small ones: utilities.getViewportContentMode answers for every viewport, AnnotationMultiSlice.setViewportFrameRange really sets the range, the 16-bit texture scale fix.

6.2 Known and not fixed

  • Fixed on 2026-11-16: a next whole slide viewport showed the slide turned by 90 degrees against the legacy viewport. It keeps the rotation that the microscopy viewer takes from the slide now. Left for the whole slide package of stage 0: its view state takes the rotation in radians where a planar viewport takes degrees, so the rotate tool would turn a slide far too much.
  • Legacy only today, closed in stage 0: the sharpening and smoothing passes (a vtk.js convolution over the drawn frame; no test covers them), the PERSPECTIVE type (a legacy volume viewport whose camera starts in perspective; its own comment says "not implemented yet", and no example uses it; the next 3D viewport already has a perspective camera through parallelProjection: false), vtk.js actors and widgets of the application in a planar viewport (addActor, setActors, getRenderer, addWidget), setAspectRatio, and a labelmap over a video.
  • Found and fixed on 2026-11-16 (80591ebe6): in an ECG trace layout with several columns a point of an annotation was drawn in the cell of another lead; scroll() of the next whole slide viewport did nothing; a next video viewport could open on its second frame and panned by the wrong amount.
  • The outline of a labelmap is not drawn on the CPU canvas. It never was.
  • Accepted, not a defect: a next viewport puts a volume slice on voxel centres, so a crosshair drag lands on 30 where the legacy viewport keeps 29.97. It is in the guide. The world crosshair tool is built for this: it keeps the exact world point by itself, each viewport shows its closest slice, and the point counts as off the slice only beyond half the slice spacing.
  • A slab through the whole volume is too much work for the CPU without workers.
  • Slope and intercept of an image that is not prescaled: both next paths follow the legacy GPU, which draws raw values.

6.3 Decided on 2026-11-16

  1. Names: plain. "yeah just call them plain names". PLANAR_NEXT, VOLUME_3D_NEXT, VIDEO_NEXT, WHOLE_SLIDE_NEXT and ECG_NEXT become PLANAR, VOLUME_3D, VIDEO, WHOLE_SLIDE and ECG, as the last mechanical step of stage 5. The codemod renames them in applications.
  2. No gap. "add them don't want any gap". Sharpening, smoothing and perspective come to the next viewports. I read it as the rule for everything a legacy viewport can do, so the other legacy-only features of 6.2 come too. This is stage 0.
  3. Slices on voxel centres: fine. "i think it is fine put it in migration guides". It is in the guide, with the world crosshair as the tool to use for an exact reference point.

The two crosshairs. CrosshairsTool is the legacy design: one centre that every camera has to follow exactly. WorldCrosshairTool with SliceIntersectionTool is the design for the next viewports: a world point that no camera owns, and the lines of the planes as a tool of their own. My default: CrosshairsTool stays in 6.0 and moves to the next API in stage 2, because of "no gap", and the guide recommends the new pair. Tell me if you want the old tool removed in 6.0 instead.

  • CPU MIP in workers, with cached frames per angle.
  • Workers that fill the cache of neighbour slices, on pages that allow shared memory.
  • The 4D window of decoded frames.
  • The GPU volume path as a module that loads on demand.
  • A WebGPU draw program. A sampler for bricks. A sampler that asks a server.

8. Risks and open questions

  1. Sampling on the main thread of a slow phone. I have no number for it. The cache of neighbour slices in 3.8 is the first answer. If it is still too slow, the choices are workers, a coarser sample while the user moves (the interactive setting already allows that), or the GPU volume as a speed-up where it fits.
  2. How an oblique slice looks. A slice sampled at voxel size and enlarged by the GPU is slightly softer than today's per-pixel sampling. The fix is to sample at screen size when the view is idle, capped at 2048. That took 12 to 46 ms here.
  3. Tools that hold vtk.js actors. 44 files in tools import vtk.js. 18 files in core and tools check for the volume slice mode. Labelmap styling has to move to the draw contract.
  4. The formats that vtk.js picks. The image mapper stays, so half float and 32-bit float stay possible on a device with no norm16. The probe fix covers norm16 only. The device set of step 0 has to show whether the other two cause wrong pictures.
  5. OHIF. It calls the legacy API today, so it cannot take 6.0 until it has moved to the next API. You said OHIF comes after Cornerstone is done. Until then it stays on 5.x.
  6. 3D on a weak device is not solved on the client. It is a reduced image by opt-in, or a server.
  7. CPU memory is the next limit. The decoded frames stay in RAM, 3 GB by default, which is more than a phone gives a page. The 4D window is the first tool for that. A default that fits the device is an open question.
  8. Uneven slice spacing. A CPU sampler can read frames at their real positions, so it could later remove the need for a regular volume. I did not look into it.
  9. Overlap with open work. #3034 (budgets per display set) and #3022 (automatic limits) solve the same failures by reducing textures. With slice first they are needed only for slabs and 3D. That should be agreed before more of it lands.
