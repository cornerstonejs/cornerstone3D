Audit of the gap work: is it worth bringing the old way?

17 November 2026. Three reviewers read every added member, its callers in this repository and in the OHIF checkout, and what the new API offers for the same job. The decisions are mine. Updated after the cut: each row says what is in the code now. The last commit is 58914567b.

The answer: no, most of it was not worth bringing. It is out now.
  • The gap work added about 3,400 lines to the new classes. 2,073 lines have left the six class files (the base class and the five families: 11,203 lines after the gap work, 9,130 now). The same jobs are done with the new API.
  • What stays is small: real fixes, and features in the new shape (a presentation key, a view state key). The six files are 2,176 lines larger than in 5.x, where they had 6,954.
  • Most added members were moved up from the adapters, as they were. They are on the adapters again, and leave with them.
  • You asked that every replacement works for a 2D stack and for a volume. Each planar row now says what the call does in both, and where one of them is not shown by a test.

Why it grew

  • Tools tested for an old name. A tool asked typeof viewport.jumpToWorld === "function". The quickest way to make it work on a new viewport was to give the viewport that name. The right way was to change the tool, and the tools are changed now.
  • The projection service was not finished. The design says zoom and pan go through viewportProjection. For a 3D viewport that call did nothing. So getZoom, setZoom, getPan and setPan were added to the class in its place. The service has zoom and pan for 3D now, and the four members are off.
  • A clean path existed and was not used. A surface in 3D went through the new addActor registry, while a geometry display set and its render path had been in the code since 5.0, unused. The surface tools use that path now.
  • Options became a second state. setOptions on every family was a second mutable place next to the view state. It is gone.

The rules I decided by

  • A viewport holds four things: its display sets, a presentation for each, a view state, and the way to turn a view into a reference and back. Nothing else is a member.
  • A question that the public state and the data can answer is a function, not a member.
  • Navigation is a view state change. Zoom and pan go through the projection service, for every family.
  • A tool that needs an old name is changed. The old name lives only on the adapter, and goes with it.

The decisions

How to read each row
  • What a caller uses instead is the call of the new API for the same job, as it was built, with one line on what it does. Each call was searched in the code after the cut.
  • Stack and Volume in a planar row say what the call does on a 2D stack and on a volume, where the two differ.
  • Public An application can call it. It is a member of the viewport, an event, or exported from @cornerstonejs/core or @cornerstonejs/tools. utilities, cache, viewportProjection and Enums are those of core unless the row says the tools.
  • Private It is inside the library only. A tool of the library uses it. An application cannot import it.
  • Not built yet One part of the replacement is still not built. The row says which part.
  • Nothing needed Nobody calls the old member, so nothing replaces it.
  • Under the decision, cut means the member is off the new class and the replacement is in the code. cut in part means that one part stays, and the row says which and why. No row says not cut yet any more. A cut member still works on the adapter.

What was built differently from the decision

Planar viewport
  • Bounds and the value at a point come from the viewport, not from the volume of the cache. viewport.getImageData() answers in stack mode too, so one call serves both modes.
  • Two functions are new, and one that this page named is private. utilities.getSlicesClippingPlanes(viewport) took the place of getVolumeSlicesClippingPlanes(volume, camera), which is private now. utilities.isInAcquisitionPlane(viewport) is new. utilities.getCurrentVolumeViewportSlice(viewport) answers for a stack too. navigatePlanarViewportToPoint is exported from the tools.
  • The reformat names stay. AXIAL_REFORMAT and the three others are values of the public enum, so a new viewport takes them. One resolver serves the mount option, setOrientation and setViewState. The audit wanted the names on the adapter only. Before, setViewState kept a name as a string and the view did not follow it.
  • A normal without a view up is not an error. The audit said that a caller gives both vectors. The class takes the view up of the acquisition for a missing one. A view up that is not orthogonal to the normal throws.
  • loop wraps in volume mode too. The legacy volume viewport ignores loop. On a new viewport utilities.scroll and the stack scroll tool wrap in both modes.
  • A slab step is the legacy snap, not delta times the slab thickness as the audit proposed. It is one slab thickness only when the depth of the volume is a whole number of slabs.
  • The adapter fires two events that it did not fire before the gap work: IMAGE_LOAD_ERROR and the calibration event when an image shows. They came with the gap work, so the adapter keeps them, through a hook of the class.
  • A slice range with a plane restriction is fixed in another place than planned. The function that the plan named, isPlanarReferenceViewable, is dead code. The fix is in isReferenceViewable of the planar class.
  • Three rows of this page were wrong, and say so now: getVolumeId() gives an id in stack mode, detail.image of STACK_NEW_IMAGE exists in stack mode only, and getImageData().scaling gave nothing for a PET stack. The third is fixed.
3D viewport and surfaces
  • The adapters keep their own stored origin. The plan put the zoom and pan members of the 3D adapter on top of the service. setZoom(value, storeAsInitialCamera) and resetCamera({ resetZoom: false }) have no meaning in a service without state, so the adapter keeps its stored camera. The whole slide adapter keeps its origin of the pan the same way.
  • hasImageURI on a 3D viewport needs an option: isReferenceViewable({ referencedImageURI }, { withNavigation: true }). The audit gave the call without it.
  • getWidget left. The audit kept three widget members on the 3D class. Two stay, and the orientation marker tool keeps its own map.
  • A reset fits a visible surface that reaches outside the volume. The legacy viewport and the adapter fit the volume only.
  • The actor registry was not harmless. After a new volume it refused the new handles of the cropping tool. The handles are props of the tool now, and leave the scene when the tool is disabled.
  • The surface of a deleted segment also leaves the 3D adapter, not only the new class. The fix is in packages/polymorphic-segmentation, where that file is, not under the surface tools.
  • invertStateChanged is on neither the 3D class nor the 3D adapter. Before the gap work the adapter fired no VOI_MODIFIED at all. A listener reads detail.invert. No code in the repository reads the flag any more.
Video, whole slide and ECG viewports
  • The video canvas has no new function. The audit wanted a function that draws the frame. Nothing read the pixels of that canvas, so the drawing left. The two tests that read them became one, which checks the size of the canvas.
  • getPan and setPan of the video stay. They are from 5.x. The right pan moved into the projection, and the two agree.
  • hasImageURI of the video failed for another reason than the audit gave. The tools handed over a target id with the loader scheme, not a URI. The fix is in the tools.
  • The pan of a whole slide is measured from the centre of the slide, not from the view at mount. setPan(pan, true), which stored the origin, has no successor.
  • The whole slide adapter has a scroll of its own now. Before the gap work it had none: it got the zoom on scroll from the class.
  • getCurrentMode() says "video" and "wholeSlide" on those viewports. It said "unknown". So utilities.isInAcquisitionPlane is true for them, and AnnotationMultiSlice asks the mode, not the type.
Base class and types
  • isDestroyed is the one new public member of the base class. The rendering engine no longer writes isDisabled on a new viewport.
  • Types.IGenericViewport no longer extends Types.IViewport. That was one of the two questions left for you. It breaks code that read a legacy member from a value of that type.
  • Nine functions take PlanarViewport beside their legacy type, not every new viewport: they read planar members. 43 functions take every new viewport.
  • toICamera() of a planar view keeps its own type. Its scale is a pair, and Types.ICamera says one number.
  • Six type assertions went into function bodies. The plan allowed annotations only. The emitted JavaScript of core and tools is the same, file by file.

Found on the way, still open

None of these is fixed. Two rows above also carry Not built yet: a fit for a stretched image, and a public read of whether a video plays.

Planar viewport
  • Stack mode names a volume that is not there. getVolumeId() gives an id and hasVolumeId() agrees, though no volume is mounted or cached. Same in 5.x. Only getCurrentMode() tells.
  • getVolumeId({ volumeId }) gives the id of the source for a volume that is not mounted. The legacy viewport gave undefined.
  • getAspectRatio() of the base class always answers [1, 1], also on a stretched view. It is from 5.x.
  • getDisplayArea() answers with the option of creation while the view state has none, and a new viewport does not apply that option. From 5.x.
  • setPan and setZoom without a point are wrong on a view with a display area. setPan drops the zoom back to the fit, and setZoom(zoom) loses the pan. The legacy stack viewport keeps both. setZoom(zoom, canvasPoint) is right. Measured, on the new viewport and on the adapter. The fix is two small changes in the resolved view of the planar viewport.
  • Reading the whole presentation and writing it back doubles the zoom on a view with a display area (zoom 2 becomes 4), on the new viewport and on the adapter. Measured. It needs a decision on what a zoom beside a display area means.
  • A named orientation that equals the acquisition becomes ACQUISITION. For an axial series whose slices run the other way, AXIAL then gives the view of the acquisition, not the axial camera. Seen in one debug run, not compared with a legacy viewport.
  • A zoom with no anchor after a pan through the service is about the centre of the slice and not about the centre of the canvas. Read, not run.
  • A slice range of an annotation has no effect on the screen in volume mode. The tools draw an annotation on a volume by where it lies. The legacy volume viewport is the same.
  • A stack with images in several orientations: a reference with a plane restriction is not viewable while another orientation shows. It is viewable on the legacy stack viewport. Read, not run.
  • utilities.jumpToSlice with the id of another volume counts the index in slices of the source and steps by the spacing of the other volume. No caller passes one.
  • isPlanarReferenceViewable is dead code. Only a test calls it.
3D viewport and surfaces
  • Without the polySeg add-on, a Surface representation with data from the application throws an uncaught error 300 ms after it is added.
  • A new colour of a segment does not show on a surface on the legacy 3D viewport or on the adapter. It is fixed on the new viewport only.
  • Removing a surface on a legacy viewport removes too much: every actor whose representation UID starts with the segmentation id, so a labelmap actor of that segmentation too.
  • A geometry display set that is registered with a reference needs imageIds: [].
  • A new 3D viewport that shows only surfaces says getCurrentMode() "empty". The tools mount a surface as an overlay, so there is no source display set.
  • cache.purgeCache() keeps geometries.
  • SegmentationIntersectionTool reads clippingFilter of an actor entry, which nothing sets, on any viewport.
Video and whole slide viewports
  • The zoom of a whole slide in the projection service is the zoom level of the map, not a factor against the fit. A zoom synchronizer between a whole slide and another family copies a number with another meaning.
  • A patch with a pan and a new rotation on a video computes the pan at the old rotation. A pan, a zoom, or both in one patch are right.
Types
  • The tools are typed with the legacy pair nearly everywhere, while they run on new viewports. Types.IEnabledElement["viewport"] is the centre of it: 170 errors in 73 files of the tools when it is widened. It is the type work of the stage that deletes the legacy interfaces.
  • Nine functions keep a legacy type. Two of them have a path for a new viewport (moveAnnotationToViewPlane, draw3D.addLine3DBetweenPoints). Three volume functions of core call getCamera with no guard.
  • A strict application gets 8 errors on the calls of the guide with strictNullChecks. 7 say that a value can be undefined. 1 is about the legacy IVolumeViewport.
  • In stack mode getImageData() is typed as a CPUIImageData, on the GPU too. So imageData is not typed as a vtk.js image data, and getBounds is optional in the type.
  • init({ rendering: { ... } }) does not compile in TypeScript without debug. Same in 5.18.3.
  • Which name stays in 6.0, Types.IViewport or Types.IGenericViewport, is yours to say.
Tests and tools
  • A zoom and pan synchronizer between a legacy viewport or an adapter and a new 3D or whole slide viewport no longer moves the new one. Its fallback needs the old members on both sides. Two new viewports sync, and two legacy ones do. It ends with the adapters.
  • IMAGE_LOAD_FAILED in volume mode is not shown by a test. The try ended early: a streaming volume with one failing image ends in an unhandled rejection of the loader.
  • The fake volume loader of the tests ignores zSpacing. A test that asks for another slice spacing does not get one.
  • packages/tools/src/utilities/viewportCapabilities.ts copies three checks that core exports. Two examples import it, so it was not deleted.
  • utilities.calculateViewportsSpatialRegistration passes a slice index to the metadata where an image id belongs. On a legacy viewport too.

Defects the audit found on the way

  • fixed The zoom tool was wrong on a new 3D viewport. The zoom limits never applied. They hold now, and the zoom goes to the mouse (c4d630ecf).
  • fixed The zoom and pan synchronizer reported success for a 3D target while nothing moved. The fault was in the 3D projection, which has zoom and pan now (c4d630ecf).
  • fixed The MIP jump to click tool threw on a new 3D viewport, at getBounds. The second commit of the cut fixed it. The tool reads the bounds from the image data of the viewport now, in both modes (88ec26951).
  • fixed The window synchronizer applied nothing to a new 3D target when the event named a volume (c4d630ecf).
  • fixed The surface of a deleted segment stayed on a new 3D viewport, and on the 3D adapter too (c41c1fd78).
All but the third were seen failing in a new test first, then fixed. The pan and the zoom tool now have tests on a new planar, 3D, video and whole slide viewport. The cut found more defects and fixed them: the list of commits at the top names them.
